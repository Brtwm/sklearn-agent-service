# Агент: исправления и продолжение курса

Сервис остаётся на шаге REST `/agent`. Gradio пока использует обычный RAG.
Следующие шаги можно добавлять поверх текущих файлов; полная замена `main.py`,
`graph.py` или `tools.py` учебным reference вернёт исправленные ошибки.

## Что сохранено для шагов 8–9

- `build_agent_graph(checkpointer=None)`, узлы `agent` и `tool_executor`.
- `messages`, `iteration_count`, `MemorySaver` и `configurable.thread_id`.
- `invoke()` и `stream(stream_mode=["updates", "messages"])`.
- `_extract_trace(messages, sources=[])` возвращает `(trace, tools_used)`.
- `AgentResponse.answer`, `trace`, `sources`, `guardrail_triggered`, `iterations`.
- Инструменты `documentation_search`, `python_repl`, `web_search` и их аргументы.

## Что отличается от примера

`AgentResponse` дополнительно возвращает `thread_id`, `total_ms` и
`termination_reason`. ID нужно сохранить и передать при следующем запросе.
Новый ID начинает другой диалог; рестарт процесса очищает MemorySaver.

Trace сопоставляет результаты по `tool_call_id`. Успешный поиск с пустым
списком документов и ошибочный/невыполненный вызов не считаются подтверждением
утверждений о документации. Это всё ещё не проверка истинности каждого утверждения.

Инструменты используют `response_format="content_and_artifact"`. Вызов с обычным
словарём аргументов по-прежнему возвращает текст. Вызов через ToolNode возвращает
ToolMessage, где `artifact` содержит время инструмента, а для поиска — исходные
чанки и URL. Эти служебные данные не отправляются LLM как текст.

`latency_ms` — время конкретного инструмента; `None` означает, что измерение
недоступно (например, для старого результата или отменённого вызова).
Общее время графа находится в `total_ms`, не в последнем шаге trace.

RAG-ресурсы FastAPI передаются инструменту через `set_rag_resources()`, чтобы
не загружать второй embedder. Сохранён startup через `_ensure_ready()`:
при недоступном индексе `/health` работает, `/ready` возвращает 503.

При лимите итераций граф завершает протокол невыполненных tool_calls сообщениями
об отмене и возвращает явный текст о незавершённой задаче. В состоянии и REST-ответе
это обозначено `termination_reason="iteration_limit"`; следующий запрос может
продолжить диалог с корректной историей.

Исключение инструмента превращается в ToolMessage со статусом error и именем
класса ошибки, без внутренних деталей. Это позволяет агенту объяснить сбой
и продолжить диалог, сохраняя пару tool_call/result.

## При добавлении Gradio-режима агента

1. Сохранить текущую общую ограниченную очередь Enter/кнопки и восстановление
   элементов управления после ошибок. Не заменять их двумя независимыми событиями.
2. В Gradio 6 не добавлять удалённый аргумент `type="messages"` к Chatbot.
3. Собрать обновления текущего запуска. `_extract_trace()` и `_extract_sources()`
   можно применить к собранным сообщениям; всю историю checkpointer передавать
   для формирования trace текущего запроса не нужно.
4. После стриминга взять итоговый AIMessage из обновлений графа и применить
   `check_output()`. Не считать накопленные токены гарантированно окончательным
   ответом: это важно при tool_calls и остановке по лимиту.
5. Показать `iteration_limit` как незавершённую задачу. Предварительные токены
   до проверки выхода могут отличаться от итогового проверенного текста.
6. Для источников использовать `_extract_sources()`, который читает исходные
   чанки из artifact и поддерживает старый текстовый блок `Sources:`.

## Проверки

В окружении с установленными `requirements.txt`:

```powershell
python -m pytest -q
```

Пример запроса PowerShell:

```powershell
$body = @{ question = "What is Ridge regression?" } | ConvertTo-Json
$reply = Invoke-RestMethod -Uri "http://localhost:8000/agent" -Method Post -ContentType "application/json" -Body $body
$reply | ConvertTo-Json -Depth 10
```

После Docker-сборки дождаться HTTP 200 от `/ready`; `sleep 5` недостаточно.
Проверить Ridge с поиском, арифметику с Python, составной запрос и продолжение
диалога с возвращённым thread_id. Промпт задаёт правила выбора инструментов,
но их соблюдение конкретной моделью требует проверки; это не принудительный router.

В реальном прогоне поиск по Ridge заработал, но вопрос про default alpha
обнаружил пробел в результатах корпуса: найденные фрагменты не подтверждали
значение. Промпт требует внешней проверки вместо подстановки из памяти.
`web_search` теперь возвращает также заголовки и URL, чтобы отличать Ridge
от RidgeCV и Lasso. Сетевой сбой или слабая выдача могут оставить задачу
незавершённой; сам факт вызова инструмента не доказывает правильность ответа.

На финальном коде составной запрос про default alpha остановился по лимиту:
поиск не подтвердил значение. Это незавершённая проверка знания, а не успешный
расчёт. Для таких вопросов полезно позже добавить страницы API классов в корпус.
Составной запрос с явно заданными alpha=0.5 и весами [2, -3] завершился поиском
формулы и вычислением штрафа 6.5 через Python.

Smoke-прогон проверяет HTTP, выбор инструментов, память и отдельные расчёты,
но не заменяет проверку фактов. Например, модель написала о безусловной
единственности решения Ridge: это требует alpha > 0; при alpha=0 остаётся OLS
и решение может быть неединственным. В сравнении Lasso/Ridge она также смешала
нормировки штрафа из разных objective functions. Эти ограничения качества
ответов зафиксированы в JSON-отчёте и требуют дальнейшей оценки grounding.

## Перед VPS

PythonREPLTool выполняет код в процессе сервиса и не является безопасной песочницей.
Текущие исправления не обеспечивают изоляцию Python. До публичного доступа нужно
изолировать выполнение либо отключить этот инструмент. Не публиковать API без
контроля доступа, ограничения нагрузки и отдельной проверки безопасности.
